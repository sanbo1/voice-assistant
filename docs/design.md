# 設計メモ（決定事項）

初期検討（2026-09-19）で決めた内容をまとめる。変更があればこのファイルを更新する。

## 目的
- ウェイクワードを検知して音声での質問を受け付け、AI チャットに投げ、返ってきた結果を音声で読み上げる。
- 基本的に無料で動く構成とする。

## ハードウェア
- 本体：Raspberry Pi 5（メモリ 16GB）、64bit 版 Raspberry Pi OS を前提とする。
  （初期検討では Pi 4（8GB）としていたが、2026-09-19 の実機確認で Pi 5 と判明したため修正）
- マイク：USB マイク（手持ち品）。
- スピーカー：開発および運用の初期は HDMI モニターのスピーカーを使う。将来、専用の USB スピーカーを購入して切り替える予定。
  - Pi 5 には 3.5mm のオーディオ端子がないため、音声出力は HDMI・USB・Bluetooth のいずれかになる。
  - USB マイク（C-Media 製 USB PnP Audio Device）は録音専用で、再生には使えない。
  - **モニターの画面が消えている間は、HDMI のスピーカーから音が出ない**（2026-09-19 確認）。
    HDMI のスピーカーを使う間は、画面の自動消灯をオフにする（`raspi-config` の Screen Blanking。2026-09-19 設定）。
    USB スピーカーに替えたら、自動消灯を戻してよい。
  - **Pi の起動時にモニターの電源が入っていないと、HDMI の音声出力が使えないままになる**（2026-09-19 確認）。
    タイマーで 30 秒ごとに確かめ、WirePlumber を再起動して直す（`tools/hdmi_audio_watch.sh`）。
- 常時稼働のため、ヒートシンクやファンなどの冷却を用意する。

## 処理構成

```
マイク → ウェイクワード検知 → 発話区間検出 → 音声認識 → AI応答 → 音声合成 → スピーカー
         (Pi上)              (Pi上)          (Pi上)    (クラウド) (Pi上)
```

| 部分 | 採用 | 代替・将来案 |
|---|---|---|
| ウェイクワード | openWakeWord（既製の英語ワード。例：hey jarvis） | 日本語の独自ワード：openWakeWord の独自学習（日本語での精度は未確認）、または Porcupine（日本語の独自ワード対応、個人利用の無料枠あり） |
| 発話区間検出 | Silero VAD（または webrtcvad） | 無音時間での打ち切り |
| 音声認識 | Vosk（日本語の小型モデル） | faster-whisper（Pi 5 では有力、要計測）、録音を Gemini に直接送る方式 |
| AI | Gemini API 無料枠（gemini-3.6-flash、思考 minimal。REST API を requests で直接呼ぶ。上限・混雑時は予備の gemini-3.5-flash-lite → gemini-3.1-flash-lite） | ほかの Gemini 3 系 Flash・Flash-Lite、Claude API（Haiku 4.5、有料）、Groq の無料枠 |
| 音声合成 | Open JTalk | VOICEVOX（Pi 5 では有力、要計測）、Piper |
| 実装言語 | Python 3 | ― |

### 方針
- AI の呼び出し部分は1つのモジュールにまとめ、差し替えられるようにする。
- 応答時間の目安（推測）：話し終わりから2〜5秒程度で読み上げ開始。
- onnxruntime（openWakeWord などが使う）の Microsoft へのテレメトリ送信は無効にする（2026-09-19 決定）。

## 会話履歴
- 初版に含める。直近数往復のやり取りをメモリ上に保持し、最後の発話から5分経ったら消去する。
- ウェイクワードなしで続けて話せる機能は、**返答のあと 3 秒だけ待つ形で実装**（2026-09-20）。
  3 秒以内に話し始めれば、そのまま続けて質問できる（1 回のウェイクワードにつき 3 回まで。`.env` で変更可）。
  **スペースキーで話し始めたときは続けて聞き取らない**（2026-09-24。回数は別の設定 `FOLLOWUP_MAX_TURNS_KEY`、既定 0）。
  利用者の希望による（ウェイクワードが反応しにくくスペースキーの利用が増えたため）。
  参考：2026-09-23〜24 のログでは、確信度の低さで雑音として弾いた 9 件のうち 8 件が、続けて聞き取る窓で起きていた
  （周りの話し声や独り言を拾ったもの）。
  誤反応対策：読み上げ終了から 0.5 秒待ってマイクを開く（自分の声の回り込み対策）、
  聞き取った文字が 2 文字未満なら AI に送らない、続けて話せる状態は短い 1 音で知らせる。
- お知らせ音は 3 種類：検知＝上がる 2 音、続けて話せる＝短い 1 音、待ち受けに戻る＝下がる 3 音（長め）。

## スペースキーの録音は、押した直後を捨てる（2026-10-04）
- スペースキーで始めた質問の頭に「ん」「と」「た」が付く問題の原因は、**押した瞬間に鳴るお知らせ音（約 0.18 秒）を
  マイクが拾い、音声認識が短い言葉にしていたこと**。実機の録音 9 件で確認した（音声認識に渡る音の先頭 0.1〜0.5 秒が
  お知らせ音の周波数で占められ、音量は話し声と同じ程度。余計な単語は先頭 0.0〜0.2 秒に付き、確信度は 0.11〜0.27）。
- お知らせ音の波形だけをデジタルで合成して試したときは再現しなかった。**スピーカーと部屋を通った本物の音でないと
  再現しない**ので、原因の切り分けは実機の録音で行う。
- ウェイクワードの回で目立たないのは、話し始めを判定する VAD を通してから認識に渡すため（推測）。
- 対策：スペースキーの回は、押した直後の `TALK_KEY_SKIP_SECONDS`（既定 0.5 秒）の音を認識に渡さず、集めもしない。
  実測では、先頭 0.2 秒を捨てるだけで 3 件とも頭の文字が消え、「今日もゴミは」などの誤認識も直った。
  話し声の始まりは押してから約 0.7 秒後だった（話し方による。早い人は小さくする）。
- 残る課題：押してから 1 秒以上待って話すと、無言の間の雑音から「えー」などが出ることがある（お知らせ音とは別の原因）。
  普段の使い方では出なかったので、対応していない。

## 伝言板（2026-10-08）
- 家族の間の伝言を、**音声で預かり、画面の右半分に出し続ける**。確認が終わったら消せる。宛先（お父さん・お母さん・個人・みんな）を
  色分けして出し、**自分宛てに、すぐ気づける**ようにする。画面と操作の仕様は `docs/display-spec.md` の 9 節。
- **伝言の内容は、AI（Gemini）に送らない。**家族の会話を外部に出さず、無料枠も使わない。会話ログ（Pi 上、7 日で消える）には、
  聞き取った文が残る。
- 入れ方：**1 回で言う**（「伝言、〜」）か、**上段の数字キーを押しながら話す**（宛先つき。本文だけ話せばよい）。
  数字キーは、音声認識の誤りに左右されず、宛名（特に個人名）を確実に指定できる。声での宛名の指定は、予備。
- 消し方：**↑↓ で選んで Delete**（2 段階。テンキーは、無いキーボードがあるので、基本にしない）、または声で「N 番を消して」→ 対象を強調して確認 →「はい」。
  声の確認は、**番号の聞き間違いへの備え**。ただし、短い「はい」は雑音として捨てられやすい（実際に確信度 0.48 の「はい」を
  捨てた記録がある）ので、確認の返事は専用に判定し、**聞き取れなければ消さない**。
  テレビの音声が「はい」と言うと確認が成立しうる（推測）ので、**消した伝言は 24 時間、Insert で戻せる**。
- **全部消す**（2026-10-08）：Ctrl+Delete → 画面の確認 → **5 秒以内にもう一度 Delete**（放置・Esc・ほかのキーは、何も消さない）、または声「伝言を全部消して」→「はい」。誤って全部消えないよう、**何もしなければ消えない側**にした。全部消した分は、Insert・声で、**まとめて**戻せる（単発の削除と区別するため、保存に「batch」の印を付ける。同じ秒に別々に消した分は、混ぜない）。
- 読み上げは短く：「預かりました」「削除します」「戻しました」。**内容は読み上げない**（60 文字の読み上げは時間がかかるため。
  必要になったら、改めて検討する）。
- 上限：**60 文字**（超えたら保存せず、「60文字までです」）、**保存は 20 件まで**（超えたら、新しい伝言を断る。
  未読を黙って失わないため、古いものを自動で消さない）。画面は 1 ページ 5 件で、矢印キーでページを送る。
  **期限切れの自動削除は、今はしない**（20 件がいっぱいになるようなら、検討する）。
- **本体が、保存・声の命令・キー操作のすべてを持つ**（`voice_assistant/board*.py`）。画面は、書かれたファイルを読んで描くだけ。
  書き込み元を 1 つにして、競合を避ける。伝言は Pi 上の `board.json`、宛先の設定は `board-settings.json`
  （どちらもリポジトリに入れない。雛形は `config/board-settings.example.json`）。

## AI を使わない回答：ごみ出し（2026-10-04）
- ごみ出しの質問に、AI に送らず、コードが予定表から曜日・第何週を判定して答える。
  AI は家のごみ収集日を知らず、「第 2・4 火曜」の計算も誤りうる（思考の量が minimal のため。推測）。
  無料枠を使わず、速く（読み上げのみ）、AI の障害時にも答えられ、判定を PC のテストで確かめられるため、
  AI に予定表を渡す方式は採らなかった。
- 答える質問（2026-10-04 に「今日」だけ作り、同日に次の段階まで広げた）：
  - 日を指す：「今日のごみは」「ごみの日」「明日のごみは」「明後日のごみは」「水曜日は何のごみの日」
  - 種類を指す：「燃やさないごみはいつ」「缶のごみはいつ」（毎週何曜日・第何何曜日と、**次の収集日**も答える）
  - 種類と日：「明日は燃やすごみの日？」（はい／いいえ）
- **答えずに AI に任せる**質問（取り違えるより AI に任せたほうがよいため）：今週・来週・昨日、「10月5日」のような日付、
  時間、複数の日や種類を同時に指す質問、日を指さない「次のごみの日」「ごみの日はいつ」、
  種類を指すが「いつ出すか」を聞いていない質問（「燃やすごみって何」）。
- 種類の名前だけ（「缶はいつ」）では、ごみの質問とみなさない。「ごみ」「収集」「捨て」「出す」のどれかが要る
  （「紙の作り方は」「缶コーヒー」などを取り違えないため）。
- 「燃えるごみ」「可燃ごみ」など、種類の別の言い方は、予定表の `aliases` に書く。答えは予定表の名前で言う。
- **続けての質問（「じゃあ明日は？」）には対応しない**。「明日は何の日」など無関係な質問を取り違えるおそれがあるため。
  ログを見て、困るようなら相談する。
- 予定表は Pi 上の `~/voice-assistant/garbage.json`。家ごとの情報なのでリポジトリには入れない（`.gitignore`）。
  雛形は `config/garbage.example.json`。質問のたびに読み直すので、直せば再起動なしで反映される。
- **予定表が無い・読めないとき**は、定型の質問に限り「登録されていません／読み込めません」と答え、AI には送らない
  （AI は家の収集日を知らず、的外れな返答になるため）。予定表と関係ないごみの質問（「ごみの分別は？」など）は
  AI に任せる。雛形を自動で写す案は採らない（ダミーの予定表を正しい答えとして話してしまうため）。
  種類の名前を含む質問を除く判定は予定表が要るので、予定表が無い間は判定が少しゆるくなる。
- 会話ログには `返答（予定表）` と書く。画面の「今日の利用」（AI の利用回数）には数えない。
  会話履歴には入れる（続けて話したときに、AI が前の答えを踏まえられる）。
- 実装：`voice_assistant/garbage.py`（判定）、`voice_assistant/assistant.py` の `_answer_locally`。

## AI サービスに関する注意（2026-09 時点の調査。変更されやすい）
- Gemini 無料枠の目安（初期検討時）：2.5 Flash は 10 回/分・250 回/日、Flash-Lite は 15 回/分・1,000 回/日。
  予告なく変更されることがあるため、公式の Rate limits ページか AI Studio で最新値を確認する。
  - 2026-09-19 時点では Rate limits ページに数値の記載がなく、AI Studio で確認する形になっていた。
    gemini-3.6-flash で約 25 秒間に 6 回送ったところで回数の上限（HTTP 429）になった。
  - **gemini-3.6-flash の無料枠は 1 日 20 回**（上限の種類：GenerateRequestsPerDayPerProjectPerModel-FreeTier。
    2026-09-19 に 429 の応答で確認）。上限はプロジェクト（API キー）ごと・モデルごと。
    対策として、上限・混雑・時間切れのときは予備のモデルで答え、上限に達したモデルは 1 時間ごとに確認して、
    回復したら優先のモデルに戻る（2026-09-19 決定）。回復の時刻は太平洋時間の 0 時（日本時間 16〜17 時）と思われる（未確認）。
- **gemini-2.5-flash は新規利用者には提供終了**（2026-09-19 に API が 404 を返し、gemini-3.6-flash を案内した）。
  モデル一覧のページでは「安定版」と表示されていても使えないことがあるため、採用前に実際に呼び出して確認する。
- **課金は有効にしない（2026-09-23 決定）。** 天気やニュースは「分からない」と答える方針を続ける。
  - 検索によるグラウンディング（天気に答えられるようにする機能）は、**無料枠では使えない**ことを実機で確認した
    （`"tools": [{"google_search": {}}]` を付けると HTTP 429。同時刻の検索なしは成功）。
  - 画像生成・動画生成も無料枠の対象外。動画は 5 秒で 40〜450 円と桁が違う。
  - 課金すれば 1 日 20 回の制限からも解放され、費用も月 $1〜2 程度の見込みだったが、
    「無料で運用する」前提を優先した。再検討する場合は `docs/improvement-options.md` を参照。
- プロジェクトで課金を有効にすると無料枠は使えなくなる。
- 無料枠で送信した内容は、Google の製品改善に使われる（料金ページに明記。2026-09-16 更新分で確認）。
- Claude の Pro プランを回答エンジンに使う案は不採用。
  理由：Pro には API の利用権が含まれない。`claude -p` を経由する方法は、規約上グレーなうえ（特に本人以外が使う場合）、
  応答が遅く、開発用の利用枠を消費する。Claude を使う場合は API 契約（従量課金）で行う。

## 開発方法
- Windows PC 上の Claude Code で開発し、`tools/deploy.sh` で Pi の `~/voice-assistant/` に配置して実行・確認する。
  Pi 側の準備（apt・venv・pip・モデル・設定）は `tools/setup_pi.sh` で行う（手順は `docs/setup.md`）。
- Pi への接続は SSH の鍵認証で行い、`~/.ssh/config` の別名 `raspi-voice` を使う。
- リポジトリは GitHub の Private リポジトリで管理する。コミットと push はユーザーの指示があるときのみ行う。

## 開発の段階
1. Pi の準備と接続確認（64bit 版 OS であるか、Python のバージョン、マイク・スピーカーの認識、録音・再生テスト）
2. 部品ごとの単体スクリプト：ウェイクワード検知 → 録音と発話区間検出 → 音声認識 → Gemini → 音声合成
   - Pi 5 のカーネルはページサイズが 16KB のため、パッケージを導入するたびに import と最小動作を確認する。
     動かない場合は 4KB のカーネル（config.txt に `kernel=kernel8.img`）への切り替えを検討する（システム設定の変更のため事前に確認）。
3. 統合：全体の処理をつなぎ、会話履歴を追加し、systemd で自動起動させる
4. 改良：日本語の独自ワード、ウェイクワードなしで続けて話せる会話、AI の切り替えなど
   - **読み上げが間延びする件は、原因を特定して対策した（2026-09-21）。**
     原因は Open JTalk 側で、句読点や空白で区切られずに続く部分が長いと、その部分を極端に長く合成する。
     例：「戦う時はゴムの実の能力で体を変幻自在に伸ばして動きます。」は 13.94 秒だが、読点を 1 つ入れると 5.10 秒。
     特定の語の問題ではなく（各語を単独や短い文で使うと正常）、無関係な文でも再現する。
     - 対策：合成に渡す前に、区切りのない部分が 20 文字を超えたら区切り（空白）を入れる（`tts.split_long_runs`）。
       空白は読点と同じ働きをし、休止も増えない。区切る位置は助詞のあと（次が漢字・カタカナのところ）を選び、
       安全な切れ目がなければ切らない。20 文字という値の根拠はコードのコメントに残した。
     - もともと間延びしない文章にも区切りが入ることがあり、わずかに不自然になる（返答 60 件中 16 件、1 件あたり +0.4 秒）。
       聞き比べて「間延びよりはよい」と判断した（2026-09-21）。しばらく運用して、気になるようなら見直す。
     - **「音声の長さの 1.08 倍を超えたら記録する」方式では、この現象は検出できなかった。**
       合成された音声データ自体が長いため、再生時間と比べても差が出ない（実機の記録も「20.6 秒の音声に 20.6 秒」）。
       音程は下がっておらず、再生側（リサンプリングやバッファ不足）ではないことも確認した。
   - 再生中の音切れは `sd.get_status()` で検出して会話ログに残す（2026-09-21。再生のしかたは変えていない）。
     間延びの原因ではなかったが、再生側の異常を見張るために残す。
   - 音声合成の声が少しこもって聞こえる件（2026-09-19）は、**対応しない**（2026-09-20 決定。運用してみて気にならなくなったため）。
     再び気になった場合は、声のデータ（MMDAgent の「メイ」など）や VOICEVOX を検討する
   - 構成ごとの改良案・ランニングコスト・リスクの一覧は `docs/improvement-options.md` を参照。
   - 以下は今後の改良案（2026-09-21 に利用者から提示。**未着手**。着手前に方針を相談する）
     - **ウェイクワードを日本語の独自ワードにする**
       - 現在は openWakeWord の既製モデル「hey jarvis」（英語）。誤反応の調整を続けているが、
         日本語の独自ワードにすれば根本的に良くなる可能性がある。
       - 候補：openWakeWord の独自学習（日本語での精度は未確認）、Porcupine（日本語の独自ワード対応）。
       - **注意（2026-09-22 調査）：Porcupine の無料枠は現状が不明確。**
