# モニター表示の仕様（検討中）

Pi につないだモニターに出す画面の仕様。**まだ作っていない。** 着手前にこの内容を見直す。

いまは会話ログを端末（lxterminal）に流しているだけ。これを専用の画面に置き換える。

## 1. 前提

### 利用者が 2 種類いる

| 利用者 | 知りたいこと | 表示の方針 |
|---|---|---|
| **家族** | いま話しかけていいか／ちゃんと聞き取れたか | 大きく、少なく、専門用語なし |
| **開発者** | 誤反応、枠の残り、調整の材料 | 小さく、数値で |

同じ画面に載せるが、**文字の大きさと位置で明確に分ける**。

### 約 5m 離れた場所から読める必要がある

2026-09-22 の測定で、実際に約 5m 離れた位置から話しかけていた。
**載せられる情報量には物理的な上限がある。** 具体的な文字サイズは実機で確認して決める。

### 家族が自然に学べる画面にする

`docs/improvement-options.md` の「人が自然と良い条件を選べるようにする」方針に沿う。

**聞き取った内容を大きく出せば、「違う言葉になっている」ことに家族が自分で気づける。**
「ワンピースのルフィ」が「いいねー１」と出ていれば、次は近づこう、静かにしようと自然に学ぶ。
技術を説明しなくても、画面が教える。

## 2. 画面構成

```
┌────────────────────────────────────────────────┐
│                                                │
│   ● 待ち受け中                                  │  特大
│     「ヘイ、ジャービス」と話しかけてください        │
│     またはスペースキーを押しっぱなしにして質問       │
│                                                │
├────────────────────────────────────────────────┤
│                                                │
│  あなた： 今日は何の日            ○ よく聞こえました │  大
│                                                │
│  返答  ： 今日は秋分の日です。昼と夜の長さが        │
│           ほぼ同じになる日ですよ。                │
│                                                │
├────────────────────────────────────────────────┤
│  ・ルフィの身長は？ → 174センチです           14:28 │  小（最大 4 件）
│  ・富士山の高さは？ → 3776メートルです         14:25 │
├────────────────────────────────────────────────┤
│ 今日の利用 12/20 回  誤反応 3  見送り 5  遅い応答 1 │  小
└────────────────────────────────────────────────┘
```

### 上部：現在の状態

| 状態 | 表示 | 色 |
|---|---|---|
| 起動中 | ● 準備中です（もう少しお待ちください） | 灰 |
| 待ち受け中 | ● 待ち受け中 ／「ヘイ、ジャービス」と話しかけてください<br>またはキーボードのスペースキーを押しっぱなしにして質問してください | 緑 |
| 聞き取り中 | ● 聞き取り中 ／ 話してください（キーで始めた場合は「押したまま話してください」） | 青（点滅） |
| 考え中 | ● 考えています… | 黄 |
| 読み上げ中 | ● 話しています | 青 |
| 続けて話せる | ● 続けてどうぞ | 緑 |

**「起動中」の表示に価値がある。** 電源投入から約 85 秒は使えないが、いまは画面を見ても分からない。

### 中央：直近のやり取り

聞き取った内容と返答を大きく出す。聞き取りの質は**確信度を記号に変換して添える**
（数値は家族には意味がないため）。

| 確信度 | 表示 |
|---|---|
| 0.85 以上 | ○ よく聞こえました |
| 0.6 以上 0.85 未満 | △ 少し聞き取りにくいです |
| 0.6 未満 | × うまく聞き取れませんでした（近くで話してみてください） |

**× のときに「近くで話してみてください」と出す**ことで、うるさいときは近づく運用へ自然に誘導する。
なお 0.52 未満は AI に送られない（`VOSK_MIN_CONFIDENCE`）ので、返答は出ない。

### 中下部：過去のやり取り（最大 4 件）

**会話の引き継ぎをしやすくするため。** 直近以外は 1 行にまとめて小さく出す。

- 会話履歴が生きている間（最後のやり取りから 5 分以内）は、**背景色を変えて「前の話が続いている」ことを示す**
- 5 分を過ぎて履歴が消えたら、薄く表示する

これで「さっきの話の続き」を言えるかどうかが画面で分かる。

### 下部：統計（開発者向け）

| 項目 | 備考 |
|---|---|
| 今日の AI 利用回数と残り枠 | **おおよその値**。無料枠のリセットは太平洋時間の 0 時（日本時間 16〜17 時）と推定されており、カレンダー上の「今日」とずれる |
| 使用中のモデル | 予備モデルに切り替わっているときだけ出す |
| 誤反応（空振り）の回数 | |
| 見送り回数 | ウェイクワードの見送りと、雑音として弾いた回数 |
| 遅い応答の回数 | **平均応答時間は出せない**（後述） |

## 3. データの入手元

| 表示 | 入手元 | 本体の改修 |
|---|---|---|
| 直近・過去のやり取り | 会話ログ | 不要 |
| 確信度の記号 | 会話ログ | 不要 |
| 統計 | 会話ログ | 不要 |
| 現在の状態 | 状態ファイル | **必要（小）** |
| 履歴が生きているか | 状態ファイル | **必要（小）** |

### 会話ログから読む

`logs/conversation.log` の各行は `MM/DD HH:MM:SS  ラベル：本文`。読む対象は次のラベル。

| ラベル | 用途 |
|---|---|
| `聞き取り（確信度 0.92）` / `聞き取り` | 直近・過去のやり取り、確信度の記号 |
| `返答` / `返答（モデル名）` | 直近・過去のやり取り、利用回数、予備モデルの使用 |
| `状態：ウェイクワードは空振りでした…` | 誤反応の回数 |
| `状態：…見送り N 回…` | ウェイクワードの見送り |
| `状態：雑音とみなして AI に送りませんでした` | 雑音として弾いた回数 |
| `状態：応答に時間がかかりました…` | 遅い応答の回数 |
| `エラー` | 異常の表示 |

**平均応答時間は会話ログからは出せない。** 毎回の応答時間は技術ログ（journald）にしかなく、
そちらは Pi の再起動で消える。平均を出したくなったら、状態ファイルに入れるか会話ログに足す。

### 状態ファイル

本体が書き、画面が読む。**`$XDG_RUNTIME_DIR/voice-assistant/state.json`（メモリ上）に置く。**
SD カードに書かないため、遅い SD カードへの負担がない。再起動で消えてよい性質の情報。

```json
{
  "state": "starting | waiting | listening | thinking | speaking | followup",
  "updated": "2026-09-23T14:30:00+09:00",
  "history_alive_until": "2026-09-23T14:35:00+09:00"
}
```

- `history_alive_until` は、会話履歴が消える時刻（最後のやり取りから 5 分後）。過去を薄く出す判断に使う
- 画面は 0.5 秒ごとに読み直す
- **本体が動いているかは `pid` で確かめる**（`/proc/<pid>` の有無）。止まっていれば古い状態を出さず、
  会話ログからの推定に切り替える。画面は本体が止まっていても動き続ける
- 別名で書いてから置き換えるので、画面が読みかけのファイルを見ることはない
- **書き込みに失敗しても本体は止めない**（画面のための情報であり、音声アシスタントの動作には要らない）

## 4. 表示しないもの

| 項目 | 理由 |
|---|---|
| **API キー** | 絶対に出さない |
| 生の技術ログ | 家族には意味がなく、画面を埋める |
| 確信度・スコアの生の数値（中央） | 家族に伝わらない。記号に変換する |
| CPU・メモリ使用率 | 判断に使えない。必要なときに調べれば足りる |
| 会話の全履歴 | 5m から読めない |

## 5. ボタンで聞き取りを始める（2026-09-23 追加）

うるさいときの逃げ道として、**ウェイクワードを使わずに聞き取りを始める手段**を用意する。
`docs/improvement-options.md` の「人が自然と良い条件を選べるようにする」方針に沿うもの。

### 押しっぱなしで録音する

**キーボードのスペースキーを押している間だけ録音する。**
画面上のボタンは**見送った**（2026-09-23）。画面が文字だけの構成のため押せるボタンを置くと
レイアウトが複雑になり、キーボードも実機のすぐ横にあって大きなキーのほうが家族に分かりやすいため。

- **マウスとキーボードは実機のすぐ横にある**ため、操作するには実機に近づくことになる。
  これ自体が「近くで話す」誘導になり、物理ボタンと同じ効果が得られる（2026-09-23 確認）。
- **録音の開始と終了が確定する。** いまは話し終わりを無音で判定しているが、テレビがついていると
  無音にならず最大 15 秒録り続け、テレビ音声を巻き込む。押しっぱなし方式ならこれがなくなる。
- キーボードなら大きなキーを狙わずに押せて、押しっぱなしも自然。マウスより家族向き。

### 受け渡しの仕組み（2026-09-23 に実装）

`$XDG_RUNTIME_DIR/voice-assistant/talk` を使う（メモリ上）。
**押している側が 0.2 秒ごとにファイルを更新し、本体は更新時刻だけを見る。中身は読まない。**
本体はウェイクワード検知のループ（80ms ごと）で確認する。

この形にした理由：

- 押している側が異常終了しても、更新が止まれば 1 秒後に自動で「離した」になる。
  「ファイルがあれば押している」とすると、残ったファイルで録音が止まらなくなる。
- 中身を読まないので、送る側の不具合で本体が想定外の動きをすることがない。
  起こりうるのは「聞き取りが始まる」ことだけで、**ウェイクワードの誤反応と同じ扱い**になる
  （短い聞き取りと低い確信度は AI に送らない、という既存の防御がそのまま効く）。
- 押しっぱなしで放置された場合に備え、録音は 15 秒で打ち切る。
- 一度離されるまで次の聞き取りを始めない（押したままでも連続して始まらない）。

### 段階

| 段階 | 内容 | 追加工数 |
|---|---|---|
| a | キー／画面ボタンで、押している間だけ録音する | +2〜2.5 日 |
| b | 物理ボタン（GPIO）を足す | +少（本体側の仕組みは a で出来ているため、ボタンの読み取りだけ） |

**段階 b で `requirements.txt` は変えない。** GPIO を読む処理は、システムの python3 で動く小さな常駐として
作り、同じ合図のファイルを更新させる（gpiozero・lgpio はシステム側に入っている）。
本体（venv）は GPIO を知らずに済み、画面が動いていなくても物理ボタンが使える。

**a で運用として有効かを確かめてから b に進む。** 部品を買う前に、
「ボタンを押して近くから話す」がご家族に受け入れられるかを検証できる。

### 実装上の注意

- **キーの自動リピートに注意。** 押しっぱなしにすると、環境によっては
  「離した」「押した」が繰り返し通知される。離された通知から数十 ms 待って、
  同じキーの押下が来ないことを確かめてから「離した」と判断する。
- 押したときは**お知らせ音を鳴らす**（ウェイクワード検知と同じ上がる 2 音。2026-09-23 決定）。
- **読み上げ中にキーを押しても無視する**（2026-09-23 決定）。ウェイクワード待ちのときだけ受け付ける。

### リスク

| リスク | 内容 |
|---|---|
| **画面アプリが本体に指示を出せるようになる** | 段階 1 は「読むだけ」で、壊れても本体は無事という安全性があった。指示を出す仕組みを入れると、その安全性が一部失われる（画面の不具合で意図しない録音が始まる恐れ） |
| 画面が落ちる・消灯するとキーも使えない | 物理ボタンなら画面と無関係に動く。b に進む理由になる |
| 画面アプリがフォーカスを失うとキーを拾えない | 全画面で常に前面に置く必要がある |

## 6. 作り方

### 本体とは別プロセス・別 Python にする

**画面が落ちても音声アシスタントは動き続ける**ようにする。画面アプリは本体の venv を使わず、
システムの python3 で動かす（tkinter はシステム側に入っている）。本体の依存関係を増やさない。

### 技術の選択

| 案 | 長所 | 短所 |
|---|---|---|
| **tkinter（推奨）** | 軽い。システム python3 に同梱。依存を増やさない | 見た目の作り込みは自前 |
| Chromium のキオスク表示＋ローカル HTML | 見栄えがよい | **重い**。ウェイクワード検知（常時 12.5% CPU）や読み上げと競合する恐れ |

起動時の読み上げが聞こえなかった事象（2026-09-21）は I/O の競合が疑われている。
**画面のために本体の動作を不安定にしないことを優先する。**

### 段階

| 段階 | 内容 | 工数 | 本体の改修 | 状況 |
|---|---|---|---|---|
| 1 | 会話ログを読んで表示 | 1〜2 日 | **不要** | **2026-09-23 完了**（`tools/display.py`・`tools/display_log.py`） |
| 2 | 状態ファイルを追加し、状態表示を正確にする | +半日 | 小 | **2026-09-23 完了**（`voice_assistant/state.py`） |
| 3 | キーで押しっぱなし録音 | +2〜2.5 日 | 中 | **2026-09-23 完了**（`voice_assistant/talk_key.py`） |
| 4 | 物理ボタン（GPIO） | 少 | 小 | 未着手 |
| 5 | 設定変更の機能 | 別途検討 | 即時反映の仕組みが前提 | 未着手 |

**段階 1 だけでも、いまの端末表示より大きく改善する。** 本体に触らないので、
壊れても音声アシスタントは動き続ける。

### 段階 1 で分かったこと（2026-09-23）

- **状態の表示は、会話ログからでもおおよそ分かる。** 段階 2 を待たずに出せている
  （「聞き取り」の直後は考え中、「返答」の直後は読み上げ中とみなす）。
  ただしログに書かれた時点でしか変わらないため、実際より遅れる。正確にするには段階 2 が要る。
- **モニターはテレビ（ORION 製）で、テレビ側の内部オーバースキャンにより端が切れる。**
  Pi 側は `disable_overscan=1` 済みだが効かない。アプリ側で余白を持たせ、
  実機で調整して `display-settings.json` に保存する方式にした（`c` キーで調整モード）。
  2026-09-23 の調整結果は上下 2.5%、左 3.0%、右 2.5%。
  なお**テレビ側の画面設定（ジャストスキャン／ドットバイドットなど）で直る可能性もある**。
- **行を画面の固定位置に置くと、下の行の背景が上の行の文字を隠す。**
  文字の高さに応じて上から積む方式にすること。

## 7. まだ決めていないこと

- **来客時の配慮** … リビングに置くため、会話の内容が来客にも見える。
  一定時間で消す、といった配慮が要るか。
- **焼き付き対策** … いま画面の自動消灯を止めている。常時表示なら深夜は暗くするなどを検討する。
- **設定変更の機能（段階 3）** … `.env` は起動時にしか読まれないため、変更のたびに
  **約 85 秒**使えなくなる。設定を即時反映する仕組みを先に作らないと実用にならない。
  また、家族の誤操作で動かなくなるのを防ぐため、変更できる項目と範囲を絞る必要がある。
- **文字サイズ** … 5m から読める大きさを実機で確認して決める。
