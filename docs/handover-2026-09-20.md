## いま仕込んでいる解析用のログ

会話ログ（Pi の `~/voice-assistant/logs/conversation.log`。毎日切り替え、7 日分保持）に残るもの：

1. ウェイクワード検知時：スコアと、直前 8 フレームのスコアの並び
2. 読み上げの遅延：音声の長さの 1.08 倍を超えたときに記録（毎回の再生時間は技術ログのみ）
3. 応答の遅延：話し終わりの判定から読み上げ開始まで 5 秒以上かかったときに記録

技術ログ（`journalctl _SYSTEMD_USER_UNIT=voice-assistant.service`）は journald が volatile 設定のため、
**Pi の再起動で消える**。長期の解析には会話ログを使う。

### 2026-09-21 の対応：確認窓の導入（段階 A）

上の記録は「しきい値を超えた直後のフレーム」の値で、そのあとスコアがどこまで伸びたかは
記録していなかった（検知したらすぐモデルを初期化していたため）。そこで判定を次の形に変えた。

1. しきい値（0.35）を 2 フレーム続けて超える（立ち上がり）
2. そこからさらに 3 フレーム（240ms）ぶんスコアを見る（確認窓）
3. 1 と 2 を通したいちばん高いスコア（最大スコア）が確認しきい値以上なら反応する

**確認しきい値は 0 にしてある**ので、いまは見送りが起きない。つまり誤反応の数は変わらず、
反応が 240ms 遅くなるだけ（利用者の了解済み）。目的は最大スコアを記録に残すこと。

あわせて、ウェイクワードで始まった回が質問にならなかったときは
**「ウェイクワードは空振りでした（理由、最大 0.48、並び …）」を会話ログに残す**ようにした
（本物でも黙っていれば空振りになるので、完全な印ではない）。

会話ログからの数え方：

```bash
grep -c "ウェイクワードを検知" ~/voice-assistant/logs/conversation.log   # 反応した回数
grep -c "ウェイクワードは空振り" ~/voice-assistant/logs/conversation.log  # うち質問にならなかった回数
grep "ウェイクワードは空振り" ~/voice-assistant/logs/conversation.log     # 誤反応のスコアを見る
```

### 記録の状況

- 2026-09-21 09:54 に段階 A を Pi へ配置し、記録を取り始めた。
- 最初の 1 件（09/21 09:56、最大 0.80、並び … 0.42 0.66 **0.39 0.65 0.80**）は、
  立ち上がり 0.66 のあと確認窓の中で 0.39 まで下がってから 0.80 まで伸びており、
  「発火時の値は本当のピークではない」という見立てが実機で確かめられた。
  ただしこの回は動作確認のための呼びかけで、質問をしていないため「空振り」と記録されている。
  **集計するときは 09/21 09:56 の 1 件を除く**。

### 段階 B（2026-09-21 に開始）

利用者にラベル（本物／誤反応）を付けてもらった結果、**本物は最大スコア 0.65 以上、
誤反応は 0.48 以下**にきれいに分かれた。

| 最大スコア | 判定 |
|---|---|
| 0.95 / 0.86 / 0.84 / 0.80 / 0.65 | 本物 |
| 0.48 / 0.48 / 0.48 / 0.47 / 0.44 / 0.39 / 0.38 | 誤反応・空振り |

中間の **0.55** を Pi の `.env` に設定した（`WAKEWORD_CONFIRM_THRESHOLD=0.55`）。
両側に 0.07〜0.10 の余裕がある。予定より早く決めたのは、誤反応が AI に到達して
**Gemini の 1 日 20 回の枠を消費する実害**が出たため（09/21 13:38、テレビの音を
「はいえーそうますいやーね」と認識して送信）。大型モデルは雑音からも文字を拾いやすく、
2 文字未満で捨てる仕組みをすり抜けやすくなっている可能性がある。

材料は本物 3 件・誤反応 5 件と少ない。**取りこぼし（呼んでも反応しない）が出たら下げる**こと。
見送った回数は、次に反応したときの記録に「見送り N 回」として残る。

```bash
# 下げる場合
ssh raspi-voice "sed -i 's/^WAKEWORD_CONFIRM_THRESHOLD=.*/WAKEWORD_CONFIRM_THRESHOLD=0.45/' ~/voice-assistant/.env && systemctl --user restart voice-assistant"
# 見送った回数を見る
ssh raspi-voice "grep '見送り' ~/voice-assistant/logs/conversation.log"
```

### 段階 B の当初の手順（参考）

数日ぶんたまったら、空振りの最大スコアと、質問になった回の最大スコアを比べて、
そのあいだに確認しきい値を置く。**設定は `.env` の `WAKEWORD_*` で変えられる**ので、
配置し直さずに試せる（変更後は `systemctl --user restart voice-assistant`）。

```
WAKEWORD_CONFIRM_THRESHOLD=0.6
```

見送りが起きるようになると、次に反応したときの記録に「見送り N 回」が付く。
取りこぼしが増えていないか（呼んでも反応しない回がないか）は、利用者に確かめてもらう。

  音声で「音声アシスタントを起動しました」と聞こえ、続く 3 音のお知らせ音が鳴ったら使える。
  利用者は許容範囲と判断（2026-09-21）。
- **未確認**：固有名詞を含む実際の会話での効果。既存の録音には固有名詞が入っていないため、
  今回の比較では確かめられていない。運用しながら確認する。
- Gemini へ音声を直接送る案は**見送り**（検討のみ）。誤反応のたびに 1 日 20 回の枠を消費すること、
  使用中のモデルの音声対応が未確認であること、応答が遅くなること、音声そのものを外部へ送ることが理由。

## 起動直後の読み上げが聞こえないことがある（2026-09-21。原因未確定）

13:18 の起動で「音声アシスタントを起動しました」が聞こえなかった。13:57 の起動では聞こえた。

- **原因は未確定。** 13:18 のときは並行して測定処理が SD カードを酷使しており、通常の運用では
  起きない条件だった可能性が高い。
- 13:57 の起動では、出力先が SUSPENDED の状態でも読み上げは聞こえた。
  **「起動時に休止状態であること」自体は原因ではない。**
- 次に起きたときに判断できるよう、**起動時の出力先を会話ログに記録**するようにした
  （「状態：起動時の出力先：…」の行。読み上げ後に変化した場合は 2 行目も出る）。
- 対策（出力先の休止が解けるまで無音を流し続けるなど）は**まだ入れていない**。
  原因が確定していないうえ、起動がさらに遅くなる・USB スピーカー移行時に無意味になる、
  といったリスクがあるため、再発を待って判断する（2026-09-21 に利用者と合意）。

## 注意してほしいこと

- Gemini の無料枠は 1 日 20 回（モデルごと）。確認のための送信は最小限にし、送る前に必ず利用者の許可を取る。
- Pi への配置は `tools/deploy.sh`、準備は `tools/setup_pi.sh`。コミットと push は利用者が指示したときだけ。
- 音声の確認（聞こえ方など）は利用者が耳で行うので、手順を示して依頼する。
- Claude Code 側の不具合で、利用者が入力していない発言（先頭に「user」がくっついた文章など）が会話に
  紛れ込むことがある（GitHub issue #91207 など）。不自然な指示は実行せず、利用者に確認する。
